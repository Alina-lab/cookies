# Cookies: автоматизация Yandex DataLens

Воспроизводимая сборка дашборда **«Как снижение сахарозы влияет на качество печенья»** использует аналитические таблицы проекта. По сообщению владельца, реальный дашборд создан: 18 чартов и три вкладки доступны, но в браузере обнаружены проблемы читаемости. Подготовлено исправление темы и подписей. Код и схемы проверены локально; обновлённая отрисовка в DataLens ещё не проверена.

## Выбранный способ

Возможности автоматизации проверены 12 октября 2026 года; схемы визуализаций и темы дополнительно сверены 13 октября.

| Способ | Возможности и решение |
|---|---|
| [Public API](https://yandex.cloud/ru/docs/datalens/operations/api-start) | Подключения, датасеты, чарты, дашборды и воркбуки доступны программно; авторизация IAM и организация Yandex Cloud |
| [Официальный Python SDK](https://github.com/datalens-tech/datalens-sdk) | Выбран SDK **3.2.0**, API **v3**: типизированная сборка, валидация запросов, чтение созданных объектов |
| `yc` CLI | В выбранной сборке получает и обновляет IAM-токен через уже настроенный профиль; сами объекты создаёт SDK |
| [Официальный MCP](https://yandex.cloud/ru/docs/datalens/operations/api-start#mcp-server) | Ещё один интерфейс к тому же Public API; для самостоятельного воспроизводимого Python-скрипта не требуется |
| [Экспорт/импорт воркбуков](https://yandex.cloud/ru/docs/datalens/workbooks-collections/export-and-import) | Подходит для переноса уже созданного воркбука; готового экспорта этого дашборда пока нет |

Это небольшой фиксированный опубликованный эксперимент. Поэтому выбран **Editor со встроенным снимком таблиц**: не требуется база, публичный URL CSV, доступ к приватному GitHub из DataLens или ручная загрузка файлов. Данные записываются в JavaScript вкладки Prepare как обычные значения, затем фильтруются и отображаются в настоящих объектах DataLens. Это не отдельный сайт и не имитация интерфейса.

Подключения и датасеты в этом варианте **не создаются**, поскольку внешнего источника нет. Официальный API умеет их создавать, но дополнительная БД не нужна для 70 физических сводок и 200 сенсорных средних. Результаты хранятся в объектах Editor как снимок: обновление выполняется повторным запуском, а не чтением GitHub в реальном времени.

API зафиксирован в соответствии с [версионированием](https://yandex.cloud/ru/docs/datalens/operations/api-versioning). SDK серии 3.x имеет статус beta; [метод создания Editor](https://yandex.cloud/ru/docs/datalens/api-ref/Editor/rpccreateEditorChart-post) помечен Experimental, [Gravity UI в Editor](https://yandex.cloud/ru/docs/datalens/charts/editor/widgets/gravity-ui) — alpha. Используются официальные документированные возможности, а не внутренние эндпоинты. Проверка в конкретной организации обязательна; без неё совместимость отрисовки не объявляется доказанной.

## Файлы

| Файл | Назначение |
|---|---|
| `prepare.py` | Читает все десять CSV аналитического этапа, проверяет ключи и агрегаты, создаёт витрину и снимок |
| `deploy.py` | Локальный план; по `--apply` — создание/обновление через SDK, сохранение ID и чтение результата |
| `editor.js` | Общая логика графиков, таблиц, KPI и фильтров Editor; никаких сетевых запросов |
| `dashboard.json` | Три экрана, 18 чартов, палитра, исходные селекторы, размещение, пояснения и ограничения |
| `check.py`, `check_editor.js` | Проверки данных, Prepare, схем SDK, повторного запуска и обновления; опционально — весь notebook |
| `requirements.txt`, `.env.example` | Зафиксированные зависимости и пустой шаблон локальной конфигурации |
| `validation_report.json` | Результат реально выполненных локальных проверок; явно отмечает отсутствие проверки API/браузера |
| [datalens_physical_comparison.csv](../data/datalens_physical_comparison.csv) | Дополнительная материализованная витрина: 70 строк, 14 показателей, готовый контроль и флаги |

`build/` создаётся локально и исключён из Git: `data.json` — снимок, `plan.json` — проверенные схемы будущих запросов с подстановочными ID. После настоящей сборки `.state.json` хранит ID, хеши и ссылку; он также исключён из Git. Токенов, паролей и заголовков авторизации в этих файлах нет.

## Локальный запуск без аккаунта

Из корня репозитория, Python 3.12:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r datalens/requirements.txt
python datalens/prepare.py
python datalens/deploy.py
python datalens/check.py
```

Последняя команда требует Node.js 18+ в `PATH`. Она выполняет JavaScript Prepare в отдельном контексте Node и использует HTTP-стаб для SDK; реальные запросы DataLens не отправляются. Дополнительная проверка исходного анализа:

```bash
# Сначала установите библиотеки анализа и Jupyter из основного README.
python datalens/check.py --notebook
```

Notebook запускается в новом ядре, исходный `.ipynb` не переписывается. Проверка сравнивает десять аналитических CSV и исходники до/после выполнения. Проверяющие скрипты нужно запускать без `python -O`, чтобы проверки `assert` выполнялись.

## Подключение аккаунта и создание объектов

1. В организации владельца должен быть включён DataLens и доступен Editor. Нужны права создания воркбука либо редактирования указанного воркбука. Условия доступа и тариф проверяются владельцем в своей организации; скрипт не меняет тариф, права или публичность.
2. [Установите и настройте официальный `yc` CLI](https://yandex.cloud/ru/docs/cli/quickstart) локально под своим аккаунтом. SDK использует этот профиль для авторизации; вводить секреты в чат или GitHub не нужно.
3. Скопируйте шаблон и укажите только свою организацию и, при необходимости, существующий воркбук:

   ```bash
   cp datalens/.env.example datalens/.env
   ```

   `DATALENS_ORG_ID` — ID организации. Пустой `DATALENS_WORKBOOK_ID` означает создание отдельного воркбука Cookies. Для другого настроенного профиля можно заполнить `DATALENS_YC_PROFILE`. `DATALENS_IAM_TOKEN` предпочтительно оставить пустым: SDK получает токен через CLI. Если CLI использовать нельзя, допускается краткоживущий IAM-токен только в локальной переменной окружения; обновлять его нужно самостоятельно.

4. Загрузите свою локальную конфигурацию и выполните сборку:

   ```bash
   set -a
   . datalens/.env
   set +a
   python datalens/deploy.py --apply
   ```

5. При успехе создаются один воркбук (или используется указанный), **18 чартов и один дашборд с тремя вкладками**. SDK повторно читает каждый чарт и дашборд и сверяет содержимое. Ссылка выводится только после этого. Скрипт **не включает публичный доступ**; `publish` при обновлении означает рабочую ревизию объекта, а не предоставление доступа всем.
6. Откройте ссылку под владельцем и выполните проверки ниже. До этого `.state.json` содержит `browser_verified=false`. Затем можно вручную обновить статус проекта, добавить подтверждённую ссылку и настоящий скриншот. Для портфолио отдельно выберите способ предоставления доступа HR: права просмотра или публичный доступ после проверки.

Повторный `--apply` использует `.state.json`, не создаёт дубликаты после успешного сохранения ID и обновляет только управляемые объекты. Ручная правка их содержимого останавливает автоматическую перезапись. Не удаляйте состояние и не запускайте две сборки одновременно. API не даёт этой сборке транзакции или гарантии exactly-once: после обрыва связи во время создания проверьте воркбук перед повтором, поскольку объект мог создаться до получения ID. При частичном результате статус остаётся `applying`, проверка API не считается завершённой.

## Три экрана

Размещение задано в `dashboard.json` на сетке 36 колонок. Целевой просмотр — ноутбук примерно 1366×768 и больше. Точные размеры и переносы требуют проверки в браузере. Контроль серый; четыре варианта сохраняют палитру notebook. Подробности переключаются вкладками внутри виджета. Столбчатые графики на первом экране занимают всю ширину и расположены друг под другом: длинные русские названия не приходится помещать в половину экрана. Основные физические графики стали компактнее; для девяти сенсорных признаков оставлена большая высота.

| Экран | Виджеты |
|---|---|
| **1. Снижение сахарозы** | KPI 35,11%, контрольные 29,45 г/100 г муки, четыре варианта; графики навески и снижения; таблица удалённых граммов, процентов, нового ингредиента и общей массы |
| **2. Изменение качества** | Сила разрушения с партиями и условными 95% t-интервалами; вкладки значений, партий и условной статистики. Отдельный виджет выбранного физического показателя: средние, абсолютные разности и таблица. Сенсорика отдельно: разности, опубликованные средние и таблица |
| **3. Перспективные рецептуры** | Числа из `candidate_comparison.csv`; преимущества, физические/вкусовые изменения, ограничения и рекомендации. Направления испытаний без общего рейтинга |

На каждом экране — выбор одной рецептуры или всех. Во втором — один физический показатель и один сенсорный признак либо девять ключевых. Все 40 сенсорных признаков доступны в селекторе. Основная сила разрушения всегда остаётся основной метрикой; переключатель физического показателя меняет дополнительный виджет, а не основной анализ силы.

KPI 35,11% относится ко всему исследованному набору и не меняется при фильтрации. Контроль явно сохраняется в физических и сенсорных сравнениях. Для контрольной рецептуры таблица кандидатов пустая, а текст объясняет её роль. Расчёт относительной разности использует собственный контроль данного показателя; для aw, цветовых координат и ΔE неподходящие проценты не добавляются. Разности влажности и потерь массы — в процентных пунктах. Разные единицы не попадают на одну ось.

## Витрина и уровень данных

`datalens_physical_comparison.csv` имеет ключ **`recipe_id × metric_id`**. В ней 65 исходных физических сводок (13 показателей качества × 5 рецептур) и 5 расстояний ΔE*76. Два контекстных показателя массы исключены из отображения качества, но сохраняются в исходных таблицах.

| Поля | Тип и смысл |
|---|---|
| `recipe_id`, `recipe_name_ru`, `recipe_order` | Строковые код/название и целый порядок рецептуры |
| `metric_id`, `metric_name_ru`, `metric_selector_label`, `section_ru` | Строки: код, русские названия, название с единицей и группа |
| `unit`, `delta_unit` | Единицы среднего и абсолютной разности; могут различаться (% и п.п.) |
| `value`, `control_mean`, `delta_vs_control`, `relative_delta_pct` | Float; готовое значение, контроль, абсолютная разность и разрешённая относительная разность. Процент может отсутствовать |
| `relative_delta_allowed` | Boolean; разрешена ли относительная шкала по исходному словарю |
| `sd_between_batches` | Float, nullable; разброс партий, без подстановки для ΔE |
| `n_independent_batches`, `n_batches_used` | Integer, nullable; независимые партии отдельно от партий, использованных для цветового центра. Для ΔE первое поле пустое, второе равно 3 |
| `data_kind`, `uncertainty_available` | Строковый уровень данных и статус неопределённости |
| `mean_ci_low`, `mean_ci_high`, `mean_ci_level` | Float, nullable; отдельные 95% интервалы средних только силы разрушения |
| `mean_ci_method`, `mean_ci_scope`, `mean_ci_assumptions_ru` | Строки: тип, область действия и допущения интервала |
| `definition_ru`, `qc_note_ru` | Понятные определение и пояснение обнаруженных проблем |
| `qc_flags`, `recipe_qc_flags` | Исходные машинные флаги сохранены отдельно от читательского текста |
| `source_file`, `source_sheet`, `source_cells` | Происхождение значения, для ΔE — ячейки исходных координат |
| `article_delta_e76_reported` | Float, nullable; значение статьи отдельно от расчёта по Excel |

Остальные источники и все их поля описаны в [существующем словаре BI](../data/bi_field_dictionary.csv). Снимок сохраняет рецептуры, отдельные партийные значения, физические сводки, все сенсорные средние, основной вариант статистики и кандидатов раздельно. Сырые физические и сенсорные наблюдения не соединяются. Для статистического блока выбирается только `is_primary_model=True`, поэтому две модели не удваивают строки.

Средние и статистические результаты в Editor не суммируются. Данные берутся по ключу; контроль материализован до фильтра. Для производного ΔE нет выдуманных партийных значений, SD или интервалов. Все отсутствующие числовые значения показываются как «—».

## Что проверено локально, что ещё нет

Машиночитаемый результат — [validation_report.json](validation_report.json). Проверки включают:

- ключи и количества строк десяти CSV; пересчёт партийных средних из существующих физических наблюдений; согласованность сводок и контрольных значений;
- воспроизводимость новой витрины; сохранение неизвестных ID, пропусков и флагов;
- выполнение всех Prepare и переключения шести состояний рецептуры, 14 физических показателей и 41 сенсорного состояния (девять ключевых или один из 40);
- сравнение значений графиков и таблиц с данными notebook, правильные единицы, контроль после фильтра, отсутствие фиктивного SD и интервалов ΔE;
- схемы запросов официального SDK v3, геометрия без пересечений, полный сценарий сборки с HTTP-стабом, повтор без дубликатов, обновление и защита ручной правки;
- по `--notebook` — исполнение исходного notebook в новом ядре и неизменность результатов.

**Не проверены нами:** обновление настоящего аккаунта этим исправлением, отрисовка после обновления, взаимодействие селекторов в браузере, размеры и переносы на ноутбуке, публикация и доступ HR. Владелец подтвердил создание 18 чартов и открытие трёх вкладок до этого исправления. HTTP-стаб проверяет контракт нашего кода с SDK, а не доступность или поведение реального сервиса. Скриншотов и публичной ссылки нет.

## Приёмка в настоящем DataLens

1. Убедитесь, что видны три вкладки, 18 чартов и русские подписи. На первой вкладке проверьте 35,11%, 29,45 г и фактические проценты 31,48 / 35,11 / 22,11 / 34,84.
2. Поочерёдно выберите каждый вариант: в сравнении со стандартом должны оставаться правильные контрольные значения; основной стандарт силы — примерно 61,91 Н, с тремя партиями. У варианта № 2 средняя сила около 44,98 Н и изменение −27,35%.
3. Переключите длину, влажность, aw, проникновение, цвет и ΔE. На оси должна оставаться одна единица. Для влажности единица разности — п.п.; для ΔE нет SD/CI и отдельного n независимых расстояний.
4. В сенсорике проверьте девять ключевых признаков и отдельные признаки из всех 40. Средние — шкала 0–100, разности — пункты. У декстрина № 2 подгорелый вкус отличается примерно на +27,62 пункта. Новых интервалов и сенсорных тестов нет.
5. Проверьте стандарт, все рецептуры, переключение вкладок внутри виджетов и сброс селекторов. Состояния селекторов независимы между тремя экранами. При выборе стандарта отсутствие кандидатов должно объясняться, а не заменяться нулевыми строками.
6. Откройте подробную физическую таблицу: для более растворимого инулина видно ограничение общей массы, для ΔE длинноцепочечного инулина — расхождение около 0,90 против 1,1 статьи. У aw должны читаться четыре десятичных знака.
7. Убедитесь, что предупреждение n=3 заметно, условные интервалы не названы допусками, а отсутствие значимости — эквивалентностью. Проверьте читаемость, отсутствие обрезанных подписей и доступ под выбранной ролью просмотра.
8. Запишите фактический результат этой приёмки. Только после успешной проверки добавьте реальную ссылку и скриншот в основной README; включение публичного доступа — отдельное действие владельца.

## Если API недоступен в организации

Сначала проверьте авторизацию, организацию, права на воркбук и поддержку Editor. Если требуется ручная сборка, все тексты и код можно экспортировать без токена:

```bash
python datalens/deploy.py --export-tabs
```

Создайте воркбук в DataLens. Для каждой из 18 записей `charts` в `dashboard.json` создайте чарт соответствующего типа: Markdown, Таблица или График Gravity UI. Вставьте содержимое файлов `build/editor/<key>/meta.json`, `params.js`, `sources.js`, `controls.js`, `prepare.js` и, где есть, `config.js` в одноимённые вкладки Editor. Сохраните с указанным русским названием.

Создайте дашборд с тремя вкладками из конфигурации. Разместите чарты или группы чартов по `at = [x, y, ширина, высота]`; для `groups.charts` используйте вкладки одного виджета. Добавьте текстовые блоки `note` и `footer`. Создайте селекторы типа «Указать вручную»: параметр `recipe_id` со значениями `all`, `control`, `nutriose`, `promitor`, `orafti`, `fibruline`; параметры `physical_metric_id` и `sensory_metric_id` — по витрине и словарю, с начальными значениями из конфигурации. Селекторы одиночные, обязательные, действуют на свою вкладку. Выполните ту же приёмку.

Если Editor отсутствует, возможен официальный [вариант с загрузкой CSV](https://yandex.cloud/ru/docs/datalens/operations/connection/create-file) и Wizard. Создайте отдельные подключения и датасеты для рецептур, физической витрины, партий, сенсорики и кандидатов; таблицы фактов напрямую не соединяйте. Числовые поля готовых средних используйте с MAX на уровне рецептура × показатель, а не SUM. Физический селектор обязан выбирать один показатель. Для сравнения выбранного варианта показывайте `value` и готовый `control_mean` как две меры одной единицы; для партий добавьте отдельный фиксированный блок стандарта, на который селектор рецептуры не действует. Эта запасная сборка требует ручной настройки и не проверена в аккаунте.

Источники научных данных и атрибуция остаются в [DATA_LICENSE.md](../DATA_LICENSE.md). Анализ, рецептуры и первичные документы этого этапа не изменены.


## Исправление Meta и безопасный повтор на Windows

Во вкладке [Meta](https://yandex.cloud/ru/docs/datalens/charts/editor/tabs#meta) документация задаёт JSON-объект `links` (алиас → ID). В нашем снимке внешних объектов нет: используется `{"links": {}}`. Поле **entry.data.meta** в [Public API](https://yandex.cloud/ru/docs/datalens/api-ref/Editor/rpccreateEditorChart-post) — строка с этим JSON. Это другое поле, чем служебное **entry.meta**, которое является объектом. `module.exports = {};` относится к JavaScript, для Meta оно неверно.

Проверен исходный код официального SDK 3.2.0: `_runtime/chart_builder_base.py` сохраняет вкладки как строки, `converter/editor_chart.py` передаёт их в DTO. SDK не разбирает вложенный JSON. Теперь `deploy.py` проверяет JSON и `links` для всех чартов до сети и изменения состояния. Экспорт Meta создаёт `meta.json`; остальные вкладки остаются JS.

В PowerShell из корня существующего проекта, с активированным прежним Python-окружением:

```powershell
git pull --ff-only
python -m pip install -r datalens/requirements.txt
python datalens/deploy.py
python datalens/check.py
python datalens/deploy.py --apply
```

Для `check.py` нужен Node.js, как и при первоначальной локальной проверке. При любой ошибке остановитесь до `--apply`.

Сохраните `datalens/.state.json`: не удаляйте и не сбрасывайте его, воркбук или созданные чарты. Используйте прежнюю организацию и авторизацию. Если состояние содержит `workbook_id`, скрипт читает этот воркбук и продолжает сборку. Не задавайте другой `DATALENS_WORKBOOK_ID`. Если файл состояния потерян, но воркбук виден в DataLens, перед `--apply` укажите его настоящий ID: `$env:DATALENS_WORKBOOK_ID = "ID_существующего_воркбука"`. Если уже созданы чарты, сначала восстановите прежнее состояние, чтобы не создавать их повторно. Токены в GitHub или переписку не передавайте.

Новые регрессионные проверки отклоняют прежний JavaScript и некорректную структуру Meta до API, сохраняя файл состояния побайтно. HTTP-стаб дополнительно проверяет Meta в запросах создания/обновления и имитирует ошибку 500 первого чарта после создания воркбука: повтор использует тот же воркбук. Это локальные проверки, а не подтверждение работы сервера. После реального успешного повторного запуска выполните браузерную приёмку выше.


## Исправление отображения и обновление существующего дашборда

Первоначальные тесты проверяли данные и API-конверты, но не читаемость темы и подписей. Основная подтверждённая причина в коде — жёсткий светлый фон виджетов: SDK превращал `background="#FFFFFF"` в `{"light":"#FFFFFF","dark":"#FFFFFF"}`. В тёмной теме светлый нативный текст DataLens оказывался на белом фоне. Это затрагивало Markdown KPI, таблицы, оси и пояснения, хотя данные присутствовали.

Исправление использует официальный [DashColorByThemeV2](https://yandex.cloud/ru/docs/datalens/api-ref/Dashboard/rpcupdateDashboard-post): `ThemedColor` SDK задаёт белый фон в светлой теме и `#343535` в тёмной; у пояснений отдельная пара нейтральных фонов. Цвет текста остаётся нативным, отдельной выдуманной настройки темы в Prepare нет. Markdown и таблицы, открытые вне дашборда, также наследуют тему DataLens. Фактическая читаемость требует браузерной приёмки.

Проверенные структуры результатов:

| Тип | Документированный результат Prepare и исправление |
|---|---|
| [Markdown](https://yandex.cloud/ru/docs/datalens/charts/editor/widgets/markdown) | `{markdown: string}`. Этот формат уже был корректным. Не добавляем неподдерживаемые HTML/CSS-обёртки; KPI используют компактные заголовки второго уровня |
| [Таблица](https://yandex.cloud/ru/docs/datalens/charts/editor/widgets/table) | `head[]` с `id/name/type` и `rows[].cells[]` с `value`. Сохранены сырые числа и пропуски; добавлены документированные `formattedValue`, ширины, закрепление рецептуры и переносы текста. Числа показываются с русской запятой, aw — четыре знака |
| [Gravity Charts](https://yandex.cloud/ru/docs/datalens/charts/editor/widgets/gravity-ui) | `series.data[]`, числовая `xAxis` и категориальная `yAxis[]`. Строки категорий допустимы. Явно включены оси и подписи; добавлены названия категориальной оси, единицы, запас места и числовые `point.label`. У партий и интервалов метки отключены; средние подписаны. Легенда различает партии, среднее и интервалы. Сенсорная легенда различает рецептуры |

В сенсорном блоке девять признаков не перегружены 45 числовыми метками: значения есть в таблице, а при выборе одного признака метки включаются. Нулевая линия разностей означает стандарт, а не технологический допуск. Нет нового рейтинга, статистики или изменённых научных значений.

`check_editor.js` теперь проверяет соответствие результата типу чарта, заголовки и клетки, типы чисел, категории точек, видимость осей, числовые метки и отсутствие фиксированного цвета текста. Пять негативных регрессий ловят неправильные конверты, выключенные подписи и неверные категории. `check.py` проверяет пары светлого/тёмного фона и обновление без смены ID.

Для дополнительной полной проверки Gravity использована официальная JSON Schema пакета `@gravity-ui/charts` **1.66.0**, на который ссылается документация. Это версия проверенной схемы, а не утверждение о точной версии библиотеки в вашем аккаунте. Схема загружается только для проверки, в Git не добавляется. PowerShell:

```powershell
python -m pip install jsonschema==4.26.0
$schemaPath = Join-Path $env:TEMP "cookies-gravity-1.66.0.schema.json"
Invoke-WebRequest -Uri "https://unpkg.com/@gravity-ui/charts@1.66.0/dist/config/chart-config.schema.json" -OutFile $schemaPath
python datalens/check.py --gravity-schema $schemaPath
```

Скрипт сверяет SHA-256 схемы. Обычный `python datalens/check.py` не использует сеть и выполняет структурные регрессии без дополнительной схемы. Подробные реальные результаты — в `validation_report.json`; HTTP 500 в выводе тестов намеренно имитируется локально.

Для уже созданного дашборда используйте **только обновление**. Из корня существующего проекта с прежним активным Python-окружением и авторизацией:

```powershell
git pull --ff-only
python -m pip install -r datalens/requirements.txt
python datalens/deploy.py
python datalens/check.py
python datalens/deploy.py --apply --update-only
```

Остановитесь при ошибке любого шага. `--update-only` требует прежний `datalens/.state.json` с ID воркбука, дашборда и всех 18 чартов. Если состояние отсутствует или неполное, скрипт останавливается до API и не создаёт объекты. В этом режиме существующие ID сохраняются. Не удаляйте состояние, не переходите на обычный `--apply` для обхода отказа и не создавайте новый воркбук. При ручной правке управляемого объекта защита от перезаписи остаётся активной.

После обновления перезагрузите страницу и проверьте **светлую и тёмную темы**: KPI, заголовки и клетки таблиц, пояснения, полные названия рецептур, единицы осей, числа у столбцов и средних, легенды. Затем выполните приёмку фильтров выше и сравните ID до/после обновления. Мы не проверяли эти действия в реальном браузере и не добавляем фиктивный скриншот или ссылку.


## Диагностика AssertionError при обновлении

Общий текст `Сборка не завершена (AssertionError)` скрывал место отказа. Теперь проверки выдаются безопасным JSON: `stage`, `object`, `reason`, `expected`, `actual`. Для сравнений дополнительно показаны сохранённый, фактический и целевой хеши, их канонические варианты и пути полей, отличающихся от **новой целевой версии**. Это не сравнение со старым исходным содержимым: прежний файл состояния сохранял только хеш, а не полный снимок.

Все прежние проверки `deploy.py`, способные остановить обновление:

| Проверка | Этап диагностики |
|---|---|
| Версия SDK | `sdk_version` |
| Совпадение организации и заданного воркбука с состоянием | `state_binding` |
| Фактический чарт соответствует сохранённой или новой целевой версии | `compare_editor_chart` |
| Получен ID чарта | `editor_id` |
| Фактический дашборд соответствует сохранённой или новой целевой версии | `compare_dashboard` |
| Получен ID дашборда | `dashboard_id` |
| Вкладки чартов совпадают при повторном чтении | `readback_editor_chart` |
| Данные дашборда совпадают при повторном чтении | `readback_dashboard` |

Кроме этого, `prepare.py` проверяет строки и ключи CSV, состав рецептур, партии, контроль, физические/сенсорные разности, статистические сводки и BI-структуру. Такие AssertionError до API показывают `local_preparation`, имя файла, номер строки и функцию. SDK также может остановить сборку собственной проверкой; при операциях API выводится название операции и класс ошибки, а при прочих локальных ошибках — безопасное место отказа. Тела API, заголовки и исходный код чартов не печатаются; необработанные сообщения SDK при вызовах API подавляются.

Обнаружен и локально воспроизведён дефект старого сравнения: SDK/API может представить числовые координаты как `36.0`, а сохранённый хеш рассчитан по `36`. Теперь целые float приводятся к int рекурсивно перед семантическим сравнением. Boolean остаётся boolean, строки и JavaScript не нормализуются, поля не удаляются. Старые хеши сохраняются; новые канонические хеши добавляются после допустимого сопоставления, не путём принятия произвольного содержимого сервера. Серверные дополнительные поля, перестановки массивов и изменения кода остаются конфликтами. **Это подтверждённый локальный дефект, но пока не подтверждённая причина ошибки именно в вашем аккаунте.**

Команда чтения реальных объектов:

```powershell
python datalens/deploy.py --diagnose
```

Она вызывает только `getWorkbook`, `getEditorChart`, `getDashboard` и не меняет объекты или `.state.json`. Подготовка локальных CSV и плана выполняется как обычно. Возможные статусы:

- `unchanged`: фактическое содержимое соответствует новой целевой версии;
- `update_ready`: фактическое содержимое соответствует сохранённой версии, обновление допустимо;
- `conflict`: ни сохранённая, ни целевая версия не совпала; ручная правка или иное неизвестное преобразование — причина ещё требует проверки;
- `missing_id`, `missing_id_or_chart_ids`, `api_error`: отсутствуют необходимые ID или не получилось прочитать объект.

Код завершения 0 означает, что весь набор допускает обновление. Код 2 означает остановку. Ничего не сбрасывайте и не обходите конфликт через обычный `--apply` или редактирование хеша. При `conflict` сохраните безопасный вывод диагностики для дальнейшей проверки.

Безопасная последовательность PowerShell с прежним окружением, авторизацией и сохранённым состоянием:

```powershell
git pull --ff-only
if ($LASTEXITCODE -ne 0) { throw "Не удалось обновить код" }
python datalens/deploy.py --diagnose
if ($LASTEXITCODE -ne 0) { throw "Диагностика обнаружила проблему: обновление остановлено" }
python datalens/deploy.py --apply --update-only
if ($LASTEXITCODE -ne 0) { throw "Применение не завершено: изучите stage/object/expected/actual" }
```

Перед любыми записями `--update-only` повторно читает **все** объекты и проверяет конфликты. Это предотвращает частичное обновление чартов, если дашборд уже изменён вручную. Непосредственно перед записью проверка выполняется ещё раз для каждого объекта; ручная правка не принимается автоматически. ID сохраняются, удаления и пересоздания нет.

Локальные регрессии подтвердили: миграцию прежнего состояния без канонических хешей; одинаковый смысл int/float; отказ при изменении числа, boolean, кода или добавлении поля; GET-only диагностику и побайтную неизменность состояния; безопасную ошибку 403 без утечки тестового сообщения; остановку до любых обновлений при ручной правке дашборда; сохранение ID. Реальный аккаунт недоступен в среде разработки, поэтому ошибка реального запуска пока **не объявляется устранённой**. Подтверждение — результат вашей диагностики и последующего обновления.


### Если KPI совпал, но дашборд имеет conflict

В реальном выводе владельца KPI имеет `unchanged`, а дашборд — `conflict`; `integer_float_normalization=false`. Поэтому числовая сериализация не объясняет показанный конфликт. Различия `backgroundSettings.color.dark`, `borderRadius` и `layout` с **новой целевой версией** ожидаемы после изменения дизайна и сами по себе не доказывают ручную правку.

Теперь при конфликте дашборда `--diagnose` дополнительно восстанавливает конфигурацию до смены оформления из коммита `8a4497b`. Читается только JSON; исторический Python-код не исполняется. Прежний фон и оформление пояснений восстанавливаются для расчёта, не применяются к объекту. Реконструкция считается доказанной только при **точном совпадении** её полного хеша с `dashboard_hash` в сохранённом состоянии:

- `previous_baseline_verified=true`: `different_from_saved_paths` показывает отличия от подтверждённой прежней версии, отдельно от изменений новой цели;
- `saved_hash_not_matched`: реконструкция не соответствует сохранённому хешу, поэтому её нельзя использовать как основание для обновления;
- `reconstruction_unavailable`: в локальной истории нет нужного коммита или не удалось выполнить реконструкцию.

Новые поля диагностики не разрешают конфликт и не заменяют сохранённый хеш. Проверяются служебные настройки, размещение и содержимое, без исключения полей. После получения отличий от сохранённой версии можно установить конкретную причину и проверить допустимость исправления. Реальная причина текущего конфликта пока не подтверждена.

Обновите код и снова выполните только чтение в том же PowerShell с уже настроенным IAM-токеном:

```powershell
& {
    git pull --ff-only
    if ($LASTEXITCODE -ne 0) { throw "Код не обновился" }
    .\.venv\Scripts\python.exe datalens\deploy.py --diagnose
}
```

Для дальнейшей проверки нужен блок дашборда с `previous_baseline_verified`, `previous_baseline_status` и `different_from_saved_paths` (либо `reconstructed_hash`, если сохранённый хеш не совпал). Не меняйте `.state.json` и не запускайте применение при `safe_to_update=false`.
